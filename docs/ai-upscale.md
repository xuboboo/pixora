# AI 超分放大：Real-ESRGAN x4v3 的端上分块推理

Pixora 的「AI 放大」模式用 **Real-ESRGAN general x4v3** 在访客自己的设备上推理，
图片不上传、不排队、不保留。这份文档记录它是怎么跑起来的，
以及每一个参数是怎么定下来的 —— 尤其是那个看起来像拍脑袋的 336 和 40。

实现分两处：分块表与「末块回退对齐」在
[`assets/js/pixora-lib.js`](../assets/js/pixora-lib.js)（`sr` 命名空间，可复用），
推理循环与进度回报在 `assets/js/main.js` 的 `srUpscale()`。

---

## 1. 模型与运行时

| | |
| --- | --- |
| 模型 | `assets/models/realesr-general-x4v3-t336.onnx`（约 5 MB） |
| 运行时 | 自托管 ONNX Runtime Web（约 22 MB）：`assets/ort/` |
| 执行提供方 | 支持 WebGPU 时用 GPU，否则回落 WASM SIMD + 多线程 |
| 输入上限 | 150 万像素（`SR.MAX_IN`），超过时明确拒绝并提示裁切 |
| 输出 | 4 倍（模型本身）；2 倍 = 4 倍结果再高质量降采样 |

模型文件名的 `t336` 不是版本号，是**导出时固定的输入边长** —— 这正是下面所有设计的起点。

---

## 2. 为什么必须分块

Real-ESRGAN 的网络本身是全卷积的，理论上能吃任意边长。但导出成 ONNX 时
输入形状被固定成 `[1, 3, 336, 336]`，运行时喂别的边长会直接报错。

于是推理变成：把大图切成若干块，每块连同周边上下文一起喂进 336×336 的固定输入，
只把**正中间那一块的输出**写回结果图。块间靠外围余量消接缝。

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `CTX` | 336 | 喂给模型的边长（含上下文） |
| `CORE` | 256 | 真正要取回的核心窗口边长 |
| `MARGIN` | 40 | 核心四周各留的上下文余量（336 = 256 + 2×40） |
| `SCALE` | 4 | 模型放大倍率 |

输入边长 336、放大 4 倍，输出就是 1344×1344；其中取回的是 `MARGIN*SCALE = 160` 像素
offset 起的 `CORE*SCALE = 1024` 方块。

---

## 3. MARGIN = 40 是怎么测出来的

选余量大小的唯一依据是**感受野**：卷积核看得见输入邻域，某一块的输出不只由它
对应的输入决定，还受邻域影响。余量给得不够，相邻两块在重叠区外沿看到的上下文不同，
拼起来就有缝。

余量按感受野半径定。这里是实测而不是查论文：

> **扰动法**：把输入左上角 8×8 换成随机噪声，跑一次推理，从输出左上角开始逐像素
> 与「无扰动」的基线比对，找到**最后一个受影响的像素下标 163**。
> 输出比输入小 4 倍，所以对应输入侧 163/4 = 40.75 像素；再扣掉这个架构本身的
> 固有偏移 7，得到感受野半径 ≈ 33.75，取整 **33.8 输入像素**。

所以 `MARGIN = 40`（覆盖 33.8 有余量），而不是「256 减 336 剩多少算多少」倒推出来的。
这个数是钉住的，不是猜的：

- **40**：分块推理与「整图一次算完」在内部逐位相同，接缝为 0
- **24**：开始出现 1/255 量级的接缝
- **8**：接缝肉眼可见

若要换成别的模型，重跑一次扰动法即可，不需要改任何其他代码 ——
分块表完全由 `CORE` / `MARGIN` / `CTX` / `SCALE` 四个常量驱动。

## 4. 分块表：末块「回退对齐」而非截断

`Pixora.sr.starts(total, core)` 给出某一条边上每块核心的起点。

```
total ≤ 256          → [0]                      整块一次算完
total = 600          → [0, 256, 344]            344 = 600 − 256
```

末块**不截断**而是回退：如果 `total - CORE` 不与步长对齐，就单独加一个起点在
`total - CORE` 的块，让它与上一块重叠。

为什么不截断：截断出来的块核心不足 256 像素，补齐后边长也就凑不到 336，
而**模型只吃固定边长**。回退那一块与上一块在重叠区算的是同一个函数，
结果严格等价，代价只是多算一次重叠部分。

覆盖性由 `tools/test-lib.mjs` 用 11 种尺寸钉住：起点递增、块间无空隙、不越界。

---

## 5. 边缘补齐：钳索引同时干了两件事

核心窗口外扩 `MARGIN` 像素后，越界的地方要填值。代码没有写「取真像素」和
「贴边复制」两条分支，而是直接把索引钳到 `[0, W-1]`：

```js
var sy = y0 - SR.MARGIN + py;
if (sy < 0) sy = 0; else if (sy >= H) sy = H - 1;
```

钳到边界以内时取到的是真实邻域像素，钳到 0 或 `W-1` 时自动就是**边缘像素复制**。
一条语句完成两件事，也少一类 off-by-one。

---

## 6. 数值一致性：为什么不需要 Math.round

模型的输出浮点范围是 `[0, 1]`，写回成字节要乘 255。这里刻意**不**用 `Math.round`。

`Uint8ClampedArray`（也就是 `ImageData` 的底层类型）的赋值语义是
**四舍五入、逢半取偶**，与 Python 侧的 `np.rint` 完全一致。直接写浮点值，
浏览器侧与 Python 侧的结果逐位相同。

验收脚本拿 Python 原生 ONNX Runtime 跑同一张图做逐像素比对：

| 指标 | 结果 |
| --- | --- |
| 最大单通道差 | **1** |
| 差 > 2 的像素数 | **0** |

差 1 只出现在「恰好在舍入边界上、两侧规则实现有极微差异」的像素，
属正常的浮点尾差，不是算法分歧。

---

## 7. 为什么 2 倍是「4 倍再降采样」

页面上给 2× 和 4× 两个档位，但**只有一个模型**。2× 由 4× 结果做高质量降采样得到，
而不是另找一个 2× 模型：

- 画质：超分模型的 4 倍输出细节远多于直接 2 倍采样，再 downsample 相当于多走一遍
  高质量重采样，细节比原生 2× 模型略好
- 体积：模型 5 MB 而不是 10 MB
- 画质文案上不夸张 —— 页面上明说「模型本身是 4 倍；2 倍由 4 倍结果高质量降采样而来」

---

## 8. 取消、进度与让出主线程

每块推理之间 `await new Promise(r => setTimeout(r, 0))`。这一行有两个作用，
都不是性能优化：

1. **进度条画得出来** —— 否则整个 `for` 循环霸占主线程，`onProgress` 的回调
   一次都不会被绘制
2. **「取消」点得到** —— 同理，按钮的 click 事件需要主线程空隙才能派发

取消用一个递增的 `token`：每块开头检查 `token.cancelled`，命中就抛错退出。
重跑会换新 token，旧循环即使还在跑也不会写坏结果。

---

## 9. 可复用性

分块逻辑不碰 DOM：输入是 `{w, h, data}`（`Uint8ClampedArray`，RGBA），
输出是起点表。`Pixora.sr.tiles(w, h)` 直接给你 `{x, y, count}`，
你自己的推理循环可以照 `srUpscale()` 的样子写，常量改 `SR` 一个对象就够。

签名与完整说明见 [`docs/api.md`](api.md)。
