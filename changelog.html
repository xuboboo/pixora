1.2.2 — 2026-10-13

严重缺陷修复。用户反馈「这个格式转换工具有严重 bug，你只是转换格式，不需要你调整宽高」—— 属实：state.width 默认值是 400，而尺寸控件与格式控件共用同一组状态，于是每一个格式转换页 都会把图片缩到 400px 宽。一张 1200×800 的照片在 /convert/png-to-jpg/ 上得到的是 400×267。

格式转换与调整尺寸是两种不同的意图，此前被混在一起，而缩放那一方还赢了默认值。 此版本把两者拆成显式模式。

修复

  • 格式转换不再改动图片尺寸
  • 根因：computeSize() 无条件套用 state.width，而该字段默认 400；

落地页只预设了输出格式，没有把尺寸置为「不缩放」的概念 - 现在 computeSize() 仅在 resize 模式生效，否则原样透传源图宽高 - ICO 的 256px 上限在两种模式下都保留——那是格式本身的定义，不是用户的缩放意图 - 输出文件名也只在真正改过尺寸时才带 _宽x高，否则保持原名与新扩展名 （此前转换页会产出 photo_1200x800.jpg 这种看着像被缩过的名字）

  • 落地页强制关闭缩放，且不污染 localStorage
  • 落地页的 ?w= / ?scale= 一律忽略：该页的契约就是「只换格式」，

接受尺寸参数等于让同一个页面有两个互相矛盾的含义 - 关键细节：落地页在内存里把缩放关掉，但不写回 state.resize。 因为 applyParams() 每次加载落地页都会 save()，直接改写状态会把「关闭」 持久化下去，导致回到首页时用户上次选的「调整尺寸」被遗忘

  • 首页状态栏在调整尺寸模式下仍声称「尺寸保持原样」
  • 状态文案只在启动时计算过一次，切换模式后没有重算。改为随模式刷新
  • 结构化数据与文案同步：softwareVersion 此前停在 1.1.0；

落地页 HowTo 的步骤 2 还在教用户「设定目标宽度 400 / 600」； SVG 相关说明也还写着「转位图前必须先设定目标宽度」

新增

  • 首页工具箱的「格式转换 / 调整尺寸」模式切换
  • 分段控件置于投放区下方，默认停在格式转换——因为它是不改变用户未要求之物的那一侧
  • 提示文案随模式切换：只换格式，图片尺寸保持原样 ↔ 可改宽高：按宽度、按原图比例，或锁定宽高比
  • 模式写入 localStorage，刷新与返回首页都记得；落地页则一律回到「只换格式」
  • 落地页的说明条：明确写出「这个页面只换格式，图片尺寸保持原样，不会被缩小」，

并给出通往完整工具箱的链接，让想同时改尺寸的人知道去哪

改进

  • 尺寸相关控件（目标宽度 / 目标高度 / 缩放方式 / 常用宽度 / 按原图比例 / 锁定宽高比 / 不放大）

统一标记 data-resize-only，由 [data-resize="off"] 的 CSS 规则整组隐藏。 刻意用 CSS 隐藏而不是从 DOM 移除——syncUI() 依赖这些元素存在， 删掉会让格式同步一起失效

  • data-resize="off" 直接写进静态 HTML，避免脚本执行前尺寸控件闪现
  • 首页功能卡片补到 9 张（3×3），新增「转换与缩放互不干扰」「35 个格式专属页」「可离线使用」
  • 工作流步骤由「设定宽度」改为「选处理方式」，反映两种模式

验收

  • 落地页 1200×800 → 1200×800（此前 400×267），三个不同目标格式逐一验证
  • 落地页忽略 ?w=600 与 ?scale=50，仍输出 1200×800
  • 首页默认同样保持 1200×800；切到「调整尺寸」后 400 宽 → 400×267，比例 50% → 600×400

1.2.1 — 2026-10-13

修复版本。1.2.0 上线后做了一轮「按项目自身定位反查缺口」的审计，发现两处真实缺陷： 总览页的站点图标与 Web App 清单全部 404，以及站点没有 404 页——用户一旦走错地址 就被交给 GitHub 的默认页，等于把 1.2.0 刚解决的「找不到入口」问题以更严重的形式重演一遍。

修复

  • 总览页 /convert/ 的 favicon、apple-touch-icon 与 web manifest 全部 404
  • 这三个 <link> 的前缀被硬编码为 ../../，从 /convert/ 解析后落到站点根之外
  • 同一页的样式表与 logo 用的是 ../，是对的——所以肉眼与截图都看不出异常
  • 根因：HEAD_ICONS 是一个硬编码前缀的常量，对 /convert/<slug>/ 正确、对 /convert/ 错误。

已改为按页面位置参数化的 headIcons(prefix)，两处调用点分别传 LOC.slug.up 与 LOC.hub.up - 该缺陷此前一直没被发现，是因为内链审计只走 <a href>，从不检查 <link href>

  • 404 页标题声称「32 种转换组合」，而其正下方就列着 35 条链接
  • 组合数被手算为 INPUTS.length × (OUTPUTS.length - 1) = 8 × 4 = 32；

正确算法是 OUTPUTS.length × (INPUTS.length - 1) = 5 × 7 = 35 ——每个输出格式在输入侧排除掉的是它自己，而不是每一个输出格式 - 改为由 INPUTS / OUTPUTS 推导的 PAIR_COUNT，并在生成时断言它与实际组合数一致， 不一致直接抛错终止构建 - 同时给审计加了一道守卫：所有页面中出现的「全部 N 种转换组合」都必须等于该页实际渲染的链接数。 首页那两处数字是手写的，此前没有任何机制阻止它们漂移

新增

  • 品牌化 404 页（404.html）
  • GitHub Pages 对任意未匹配路径都会返回该文件，因此它是走错地址的用户看到的最后一屏。

页面带有与首页相同的 35 条格式索引、8 个热门转换入口，以及回到工具箱 / 首页 / 总览页的三个出口 - robots 为 noindex, follow：页面本身绝不参与排名，但其中的链接仍应被抓取 - 刻意不声明 canonical——404 页面对应任意 URL，声明 canonical 等于谎称它是另一个页面 - 用一段渐进增强脚本回显实际请求的路径，让用户知道自己在哪走错了 - 路径全部使用站点绝对前缀（/pixora/…）而非相对路径：GitHub Pages 渲染该文件时 地址栏仍是原始请求 URL，相对路径会解析到一个可能根本不存在的目录。 也没有采用 <base>——它会把 #main 跳转链接一并指向首页

改进

  • 内链审计升级为「链接 + 资源」双层，并显式建模部署前缀
  • 覆盖 <a href> / <link href> / <script src> / <img src> / <source src> / <video src>，

单次审计从 2 138 条增至 2 187 条内链 + 266 条资源引用 - 新增解析器自检：内置 10 个用例，其中 3 个是历史 bug 反例（旧 favicon 前缀、旧死链写法、多退一级）， 自检不通过则整个审计直接退出——避免审计脚本自己悄悄失效 - 关键修正：仅按文件系统解析不足以发现 favicon 那类问题。本地站点根与服务根是同一个目录， path.join 会在根部静默吞掉 ..；而线上站点位于 /pixora/ 之下，向上越界即落到部署之外。 解析器因此改为自行维护目录段栈，越出站点根会被明确报告而不是被静默钳制

验收

只有真正可编码的格式才会出现在下拉框里（因此 AVIF 只在支持的浏览器上出现） - 手写 BMP 编码器：BITMAPFILEHEADER + BITMAPINFOHEADER + 24-bit BGR 自底向上像素数据， 行按 4 字节对齐（rowSize = ((24 × width + 31) >> 5) << 2） - 手写 ICO 编码器：22 字节 ICONDIR/ICONDIRENTRY + 内嵌 PNG，最长边超过 256px 时自动等比缩到 256 - 手写 ZIP 打包：Local File Header + Central Directory + EOCD 完整结构， CRC32 查表实现，优先使用 CompressionStream("deflate-raw") 压缩、不可用时降级为 store 模式 - 透明背景处理：目标格式不支持 alpha（JPG / BMP）时，自动弹出背景填充色选择器， 把透明区域合成到指定底色，避免出现黑块 - 体积变化提示：每张结果卡片显示相对原图的体积变化（↓29% / ↑679%） - 「用当前设置重转」：改完设置不必重新拖图，直接对已有结果重跑 - 「打包下载 ZIP」：批量结果一键打包，文件名形如 pixora-20261013.zip - ICO 专用预设：选中 ICO 时，宽度预设自动切换为图标尺寸 16 / 32 / 48 / 64 / 128 / 256 - 解码回退链：createImageBitmap 失败时回退到 <img> 解码（覆盖 SVG 等场景）
